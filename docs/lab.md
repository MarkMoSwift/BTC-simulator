# 实验手册：把矿工改快

课堂上的挖矿速度比赛，比的是**你自己写的矿工**能在一秒钟里算出多少哈希。
服务端会重新验算每一份份额，所以只有真的算得快才算数。

## 目标

1. 看懂一份真实矿工程序在做什么。
2. 找到"重复计算"和"数据转换"这两类浪费，并把它去掉。
3. 用实测数据证明改进有效，而不是凭感觉。

## 第一步：先量出基线

1. 用浏览器打开学生入口，正常登录，让它挖 30 秒。
2. 记录控制台上的三个数字：**实时算力**、**份额难度**、**提交份额**。
3. 打开投影大屏看一眼排行榜，服务端统计的算力应该和本地读数接近。

实时算力有波动，取稳定后的数值；建议用"从第 10 秒到第 30 秒的读数"做对比。

## 第二步：载入你自己的矿工

1. 复制 `app/web/static/miner.js` 到你自己的文件夹，比如 `my-miner.js`。
2. 删掉第一行 `importScripts("crypto.js")`（平台已经帮你加载好了 `SimCrypto`）。
3. 改代码，保存。
4. 在学生控制台的挖矿面板点「自定义矿工」，选中 `my-miner.js`。
5. 状态栏会显示"自定义矿工"，实时算力立刻反映新程序的速度；点「用回默认」可以随时还原。
6. 份额被服务器拒绝时挖矿面板会写明原因，改代码卡住的时候先看这一行。

矿工运行在浏览器的 Web Worker 里，和页面的消息协议见
[`mining-protocol.md`](mining-protocol.md) 第 6 节：收到 `{type:"job"}` 开始算，
算到份额发 `{type:"share"}`，想显示算力就定时发 `{type:"progress", hashes}`。

## 第三步：四个可以动手的地方

默认矿工是故意写直白的。下面四点都可以独立改进，建议一次只改一处，改完再测一次。

### 1. 每一轮都在重算梅克尔根和区块头（收益最大）

现在每个 nonce 都从 `tx_ids` 重算一遍梅克尔根，再重新拼一个 84 字节的头。
但一份作业里 `prev_hash`、梅克尔根、时间戳、难度、`miner_tag` 都是固定的，
变的只有最后 4 个字节的 nonce。

提示：算一次前缀存下来，循环里只写最后 4 字节：

```javascript
const header = new Uint8Array(84);
header.set(prefixBytes, 0);          // 0-79 字节固定

for (let nonce = 0; nonce < end; nonce += 1) {
  header.set(SimCrypto.toUint32LE(nonce), 80);
  const digest = SimCrypto.sha256d(header);
  // …
}
```

### 2. 每个哈希都要转成十六进制和 BigInt

现在的写法是 `bytesToHex(sha256d(header))` 再 `BigInt("0x" + text)`，为了比较一次目标值，
做了几百次字符串和 BigInt 运算，比哈希本身还贵。

提示：目标值 `share_target` 是固定的大整数，可以直接比较字节数组：
从第 0 字节开始比，遇到第一个小于/大于就结束；只有全部相等时才需要慢慢比。
也可以先把 `share_target` 转成 8 个 32 位整数，逐字比较。

### 3. 批次太小，汇报太频繁

`BATCH_SIZE = 400` 意味着每 400 个 nonce 就要 `postMessage` 一次并让出主线程。
浏览器里一次哈希只要几微秒，消息开销反而是可见的。

提示：把批次放大到几万，并且只在批次结束时汇报一次算力；份额消息仍然要立刻发。

### 4. 只用了一个 Worker

浏览器一般有多核，`navigator.hardwareConcurrency` 会告诉你这个设备有几个逻辑核心。

提示：开多个 Worker，每个负责 nonce 空间的一段（例如 `nonce % workers === index`），
它们共享同一份作业，各自提交自己的份额。注意页面上的算力要把几路加起来。

再往上一步，可以把 SHA-256 换成 WebAssembly 实现（例如用 C 或 Rust 编译），
或者把 nonce 搜索改成一次处理 4 个 nonce 的 SIMD 风格批处理。

## 参考数据

同一台电脑、单线程、同样算 4 万个哈希：

| 写法 | 速度 | 说明 |
| --- | --- | --- |
| 默认写法 | 约 26 kH/s | 每轮重算梅克尔根 + 转十六进制 + BigInt 比较 |
| 缓存前缀 + 字节比较 | 约 142 kH/s | 只做这两处改动 |

差 5 倍以上。多开 Worker 还能再乘上核数，但排行榜上显示的是你真正提交并验证通过的工作量。

## 进阶：不用浏览器也行

不想改 JavaScript 的同学，可以按 [`mining-protocol.md`](mining-protocol.md) 用 Python、Go、
Rust 写一个独立矿工：[`examples/python_miner.py`](../examples/python_miner.py) 就是一份
可以直接运行的参考实现：

```bash
pip install ecdsa
python examples/python_miner.py --base http://<课堂服务器>:8000 --nickname 你的昵称 --seconds 60
```

它演示了登录签名、组装区块头、缓存前缀、提交份额的完整流程；把它改成多进程并行就是一份不错的作业。

## 实验报告

提交内容：

1. 你的 `my-miner.js`（或你自己的矿工源码）。
2. 改动前后的实时算力截图或读数表，注明测试时长。
3. 一句话说明每一处改动为什么更快。
4. 如果做了多 Worker 或 WebAssembly，说明你是怎么验证结果仍然正确的（份额有没有被拒绝）。

思考题：

1. 为什么区块头要在开挖前就固定下来？如果等挖到再分配奖励，会有什么问题？
2. 服务端为什么要把每个 nonce 重新算一遍哈希，而不是相信客户端上报的工作量？
3. 如果全班都用了多 Worker，难度会自动发生什么变化？为什么比特币要用同样的机制？
4. 你把速度提高 5 倍后，累计挖矿排行榜上的收入会不会也变成 5 倍？为什么？
